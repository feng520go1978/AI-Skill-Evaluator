## Research plan: “Is WebSocket or Server-Sent Events better for a live dashboard?”

Before deciding, I would treat this as an engineering tradeoff question rather than a protocol popularity question. The answer depends on the dashboard’s update pattern, scale, latency requirements, and operational environment. I would research it in the following way.

---

## 1. Define the dashboard requirements first

**Goal:** Avoid comparing technologies in the abstract.

I would collect requirements such as:

| Dimension | Questions to answer |
|---|---|
| Data flow | Is it only server → browser updates, or does the browser need to send frequent messages back? |
| Latency | Is “within 1 second” acceptable, or is sub-100ms required? |
| Update frequency | Are updates once per minute, once per second, or hundreds per second? |
| Number of users | 10 users? 10,000 concurrent viewers? |
| Payload size | Small JSON events or large binary data? |
| Reliability | Must clients recover missed events automatically? |
| Infrastructure | HTTP proxy/CDN/load balancer constraints? |
| Browser support | Any legacy browsers or only modern environments? |

Example dashboard categories:
- **Business KPI dashboard:** likely low-frequency, server-to-client only.
- **Trading/operations monitoring:** higher frequency and lower latency.
- **Collaborative control panel:** requires two-way interaction.

---

## 2. Gather primary technical sources

I would prioritize specifications and official documentation over blog comparisons.

### WebSocket sources
- The WebSocket protocol specification (RFC 6455)
- Browser WebSocket API documentation
- Major framework documentation:
  - Node.js WebSocket libraries
  - Java/Spring WebSocket support
  -.NET WebSocket implementations

Things to verify:
- Full-duplex communication model
- Connection lifecycle
- Ping/pong handling
- Reconnection responsibilities
- Scaling patterns

### Server-Sent Events sources
- WHATWG HTML specification for Server-Sent Events
- Browser EventSource API documentation

Things to verify:
- Server → client streaming behavior
- Automatic reconnection behavior
- Event IDs and replay support
- HTTP compatibility

SSE is designed around server-to-client event streaming, while WebSockets provide persistent bidirectional communication. 

---

## 3. Compare architectural characteristics

I would build a comparison matrix:

| Area | WebSocket | SSE |
|---|---|---|
| Direction | Two-way | Server → client |
| Transport | WebSocket protocol over upgraded TCP connection | HTTP streaming |
| Browser API | WebSocket API | EventSource API |
| Reconnection | Usually application-managed | Built-in browser reconnection behavior |
| Binary data | Supported | Primarily text/event streams |
| Infrastructure compatibility | Can require WebSocket-aware infrastructure | Works naturally with HTTP infrastructure |
| Complexity | Higher | Simpler |

The key question would be:

> Does the dashboard need the client to continuously send messages back?

If no, SSE may eliminate unnecessary complexity.

---

## 4. Review real-world implementation evidence

I would examine:

### Engineering case studies
Look for:
- Monitoring dashboards
- Analytics platforms
- IoT dashboards
- Financial systems
- DevOps tools

Questions:
- How many concurrent connections?
- What infrastructure was used?
- What failure modes appeared?
- How were reconnects handled?

### Open-source implementations
Compare examples such as:
- WebSocket-based dashboards
- SSE-based monitoring systems

Review:
- Code complexity
- Operational requirements
- Scaling approaches

---

## 5. Perform controlled benchmarks

I would not rely only on published benchmarks because results vary by implementation.

Build a small test system:

### Test scenarios

**Scenario A: Basic dashboard**
- 10,000 clients
- One JSON update every second
- Server broadcasts identical metrics

Measure:
- CPU usage
- Memory
- Network bandwidth
- Connection stability

**Scenario B: High-frequency dashboard**
- 1,000 clients
- 100 events/sec
- Small messages

Measure:
- Latency distribution
- Dropped events
- Backpressure behavior

**Scenario C: Interactive dashboard**
- Users send commands back
- Server pushes status changes

Measure:
- Round-trip latency
- Implementation complexity

Metrics:
- p50/p95/p99 latency
- Messages delivered
- Server resource consumption
- Recovery after disconnect

---

## 6. Verify operational concerns

I would investigate:

### Load balancing
Questions:
- Does the system require sticky sessions?
- Can connections move between servers?
- How does horizontal scaling work?

### Failure recovery
Test:
- Browser sleeping
- Network interruption
- Server restart
- Proxy timeout

### Security
Verify:
- Authentication methods
- Authorization per stream
- Connection limits
- Abuse prevention

---

## 7. Evaluate total engineering cost

The final decision should include:

- Development effort
- Debugging complexity
- Infrastructure requirements
- Monitoring requirements
- Future feature needs

A technology that is slightly faster but twice as complex may not be the better choice.

---

# Expected decision framework

After research, I would likely reach a decision using rules like:

**Choose SSE when:**
- The dashboard mostly displays live data.
- Updates flow only from server → browser.
- Simplicity and HTTP compatibility matter.
- Examples: metrics dashboards, notifications, live reports.

**Choose WebSocket when:**
- The dashboard requires real-time interaction.
- Users send frequent commands.
- You need bidirectional communication.
- Latency is extremely sensitive.

This conclusion would then be validated against the specific dashboard requirements rather than chosen universally. WebSocket’s main advantage is bidirectional communication, while SSE’s strength is simpler one-way event streaming. 

---

## Final research deliverable

I would produce:

1. Requirements summary  
2. Source review (specifications + implementation evidence)  
3. Feature comparison table  
4. Benchmark results  
5. Operational risk analysis  
6. Recommendation with assumptions  
7. “When to revisit the decision” criteria

The research question is therefore not “Which protocol is better?” but:

> “For this dashboard’s traffic pattern and operational constraints, which protocol provides the lowest complexity while meeting latency and scalability requirements?”
