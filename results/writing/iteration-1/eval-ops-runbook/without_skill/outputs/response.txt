# Nightly Data Import Failure Recovery Runbook

## Purpose

This runbook describes how an operator can diagnose and recover from a failed nightly data import. The import process:

1. Downloads source CSV files from an SFTP server.
2. Validates and transforms CSV data.
3. Loads transformed data into PostgreSQL.

Use this procedure when the nightly import job reports failure, produces incomplete data, or does not complete by the expected time.

---

# 1. Confirm the Failure

## 1.1 Check the import job status

1. Open the job scheduler or monitoring dashboard.
2. Locate the nightly import job.
3. Confirm:
   - Job status is failed.
   - Failure timestamp.
   - Last successful run.
   - Failed pipeline stage (SFTP download, transformation, or database load).
4. Record the following information:
   - Run ID / execution ID.
   - Error message.
   - Log file location.
   - Affected import date.

## 1.2 Check whether a partial import occurred

Before rerunning anything:

1. Check the importer logs for completed stages.
2. Determine whether:
   - Files were downloaded successfully.
   - CSV transformations completed.
   - Database load began or finished partially.
3. Do not rerun the import until you know whether cleanup is required.

---

# 2. Diagnose SFTP Download Failures

Use this section if the failure occurred while retrieving CSV files.

## 2.1 Verify SFTP connectivity

1. Confirm the SFTP server is reachable.
2. Test authentication using the importer service account.
3. Check:
   - Credentials have not expired.
   - SSH keys are valid.
   - Network access is available.
   - The SFTP directory exists.

Example checks:

```bash
sftp importer_user@sftp.example.com
```

Verify the expected files are present:

```bash
ls /incoming/
```

## 2.2 Validate source files

Confirm:

- Expected files exist.
- File names match the expected pattern.
- File timestamps correspond to the current import cycle.
- Files are not empty.
- Files are fully uploaded.

If files are missing:

1. Contact the upstream data provider.
2. Request the missing files.
3. Do not manually create replacement files unless approved.

## 2.3 Retry the download

After confirming SFTP availability:

1. Clear any incomplete downloaded files from the staging directory.
2. Restart the import from the download step.
3. Monitor logs for successful file retrieval.

---

# 3. Diagnose CSV Transformation Failures

Use this section if files downloaded successfully but transformation failed.

## 3.1 Review transformation logs

Look for errors related to:

- Invalid CSV formatting.
- Missing columns.
- Unexpected column names.
- Invalid dates.
- Invalid numeric values.
- Encoding problems.
- Duplicate records.

## 3.2 Validate the input CSV files

Check:

- Header row matches the expected schema.
- Required columns exist.
- Row counts are reasonable compared with previous runs.
- File encoding is correct.
- Delimiters and quoting are valid.

Example checks:

```bash
head -5 source_file.csv
wc -l source_file.csv
```

## 3.3 Correct source issues

If the source CSV is invalid:

1. Identify whether the issue is caused by:
   - Upstream data generation.
   - A schema change.
   - A corrupted file.
   - A transformation bug.
2. If upstream data is incorrect:
   - Request corrected files.
   - Replace the staged files.
   - Restart the import.
3. If the transformation code failed:
   - Escalate to the engineering owner.
   - Do not modify production transformation logic without approval.

---

# 4. Diagnose PostgreSQL Load Failures

Use this section if transformation succeeded but loading into PostgreSQL failed.

## 4.1 Check database connectivity

Verify:

- Database server availability.
- Credentials.
- Connection limits.
- Network connectivity.

Example:

```bash
psql -h postgres.example.com -U importer_user -d target_database
```

## 4.2 Check for database errors

Review logs for:

- Constraint violations.
- Duplicate keys.
- Missing tables.
- Permission errors.
- Disk space issues.
- Locking or blocking transactions.

Common checks:

```sql
SELECT now();

SELECT count(*) FROM target_table;
```

## 4.3 Handle partial loads

Before rerunning:

1. Determine whether the load was transactional.
2. Check whether rows were partially inserted.
3. Follow the application-specific rollback procedure.

Possible actions:

- Roll back the failed transaction.
- Truncate staging tables.
- Remove partial batch records.
- Restart from the database load stage.

Do not manually delete production records unless the recovery procedure requires it.

---

# 5. Rerun the Import

Only rerun after the root cause has been addressed.

## 5.1 Prepare for rerun

Confirm:

- Source files are available.
- Staging directories are clean.
- Previous failed artifacts are handled.
- Database state is ready.

## 5.2 Start the import

Run the importer using the normal operational method:

- Scheduler retry button.
- Import command.
- Recovery workflow.

Use the appropriate restart point:

- Restart from SFTP download if files were not retrieved.
- Restart from transformation if files were downloaded.
- Restart from database load if transformed files are valid.

## 5.3 Monitor execution

Confirm each stage completes:

- SFTP download: successful.
- CSV transformation: successful.
- PostgreSQL load: successful.
- Validation checks: successful.

---

# 6. Validate Successful Recovery

After completion:

1. Confirm job status is successful.
2. Compare imported record counts with expected values.
3. Run validation queries.
4. Confirm downstream systems can access updated data.
5. Check monitoring dashboards for errors.

Document:

- Failure cause.
- Recovery steps performed.
- Time to recovery.
- Any follow-up actions.

---

# 7. Escalation Guidelines

Escalate when:

- SFTP files are missing and cannot be regenerated.
- Credentials or access permissions fail.
- Source schema changes unexpectedly.
- Transformation logic requires code changes.
- Database corruption or data repair is required.
- Import cannot complete after one controlled retry.

Include:

- Job run ID.
- Timestamp.
- Relevant logs.
- Error messages.
- Steps already attempted.

---

# 8. Post-Incident Follow-Up

For recurring failures:

- Add monitoring alerts for the failed stage.
- Improve validation checks.
- Document new failure modes.
- Review retry automation.
- Update this runbook with confirmed fixes.:::
