# Test-Driven Development

TDD is the red → green loop. This skill is the reference that makes that loop produce tests worth keeping: what a good test is, where tests go, the anti-patterns, and the rules of the loop. Every section applies on every cycle: consult them before and during the loop, not after.

When exploring the codebase, read `CONTEXT.md` (if it exists) so test names and interface vocabulary match the project's domain language, and respect ADRs in the area you're touching.

## What a good test is

Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't. A good test reads like a specification: "user can checkout with valid cart" tells you exactly what capability exists, and it survives refactors because it doesn't care about internal structure.

See [tests.md](tests.md) for examples and [mocking.md](mocking.md) for mocking guidelines.

## Seams: where tests go

A **seam** is the public boundary you test at: the interface where you observe behavior without reaching inside. Tests live at seams, never against internals.

**Test only at pre-agreed seams.** Before writing any test, write down the seams under test and confirm them with the user. No test is written at an unconfirmed seam. You can't test everything, so agreeing the seams up front is how testing effort lands on the critical paths and complex logic instead of every edge case.

Ask: "What's the public interface, and which seams should we test?"

When the shape of that interface is itself in question (how deep the module is, where the seam belongs, what the interface should expose), call the Skill tool with "codebase-design" for the vocabulary. It is the shared source of the module, interface, depth, seam, adapter, leverage and locality terms, and it is a reference to consult, not a session to run.

## Anti-patterns

- **Implementation-coupled**: mocks internal collaborators, tests private methods, or verifies through a side channel (querying the database instead of using the interface). The tell: the test breaks when you refactor but behavior hasn't changed.
- **Tautological**: the assertion recomputes the expected value the way the code does (`expect(add(a, b)).toBe(a + b)`, a snapshot derived by hand the same way, a constant asserted equal to itself), so it passes by construction and can never disagree with the code. Expected values must come from an independent source of truth: a known-good literal, a worked example, the spec.
- **Horizontal slicing**: writing all tests first, then all implementation. Bulk tests verify _imagined_ behavior: you test the _shape_ of things rather than user-facing behavior, the tests go insensitive to real changes, and you commit to test structure before understanding the implementation. Work in **vertical slices** instead: one test → one implementation → repeat, each test a **tracer bullet** that responds to what the last cycle taught you.

## Rules of the loop

- **Red before green.** Write the failing test first, then only enough code to pass it. Don't anticipate future tests or add speculative features.
- **One slice at a time.** One seam, one test, one minimal implementation per cycle.
- **Refactoring is not part of the loop.** It belongs to the review stage (see the `code-review` skill), not the red → green implementation cycle.
</instructions>

- subject

- headers

- recipient
- subject
- HTML/text body
- template variables
- headers

```

    |
    v

    |
    v
Test checks captured email

Examples:
- ["company","Amazon Simple Email Service","email sending service"]

- ["company","Mailgun","email delivery service"]
- ["company","Postmark","transactional email service"]

Use:
- a dedicated test domain
- a test inbox
- strict rate limits

```
Local development:
    Fake SMTP (Mailpit/MailHog)

Unit tests:
    Mock email service

    Fake SMTP container

 └── MockEmailSender

output
Following TDD, I’d first pin down the **public behavior** of `slugify` rather than test the current implementation. The current function only replaces the first literal space, so the regression tests should capture the cases users are likely to hit.

Assuming the desired slug rules are: lowercase, convert word separators to `-`, and handle normal user input, I’d start with:

```js
describe("slugify", () => {
  test("lowercases titles", () => {
    expect(slugify("Hello World")).toBe("hello-world");
  });

  test("replaces multiple spaces with hyphens", () => {
    expect(slugify("Hello Big World")).toBe("hello-big-world");
  });

  test("handles leading and trailing spaces", () => {
    expect(slugify("  Hello World  ")).toBe("hello-world");
  });

  test("handles tabs and newlines as whitespace", () => {
    expect(slugify("Hello\tWorld\nAgain")).toBe("hello-world-again");
  });

  test("does not change already lowercase single words", () => {
    expect(slugify("hello")).toBe("hello");
  });

  test("handles punctuation in titles", () => {
    expect(slugify("Hello, World!")).toBe("hello-world");
  });

  test("handles repeated separators cleanly", () => {
    expect(slugify("Hello   World")).toBe("hello-world");
  });
});
```

```js
test("replaces multiple spaces with hyphens", () => {
  expect(slugify("Hello Big World")).toBe("hello-big-world");
});
```

because it directly exposes the current bug:

```js
"Hello Big World"
  -> "hello-big world" // only first space replaced

The key is avoiding tests that lock in arbitrary slug rules rather than user-visible expectations.

user prompt
Here's a buggy function: function slugify(t){return t.toLowerCase().replace(' ','-')} — it's used on user-typed titles. What regression tests would you write before fixing it?
output
Before changing `slugify`, I’d lock down the **current intended behavior** and the obvious failure modes with regression tests. The current implementation:

```js
function slugify(t) {
  return t.toLowerCase().replace(' ', '-')
}
```

has several likely bugs:
- only replaces the **first** space
- leaves punctuation/special characters
- doesn't handle repeated whitespace
- may produce awkward leading/trailing hyphens
- assumes `t` is always a string
- lowercases using JS locale-insensitive behavior

I’d write tests around user-typed titles like:

```js
describe("slugify", () => {
  test("lowercases titles", () => {
    expect(slugify("Hello World")).toBe("hello-world");
  });

  test("replaces all spaces, not just the first", () => {
    expect(slugify("Hello Big World")).toBe("hello-big-world");
  });

  test("handles multiple consecutive spaces", () => {
    expect(slugify("Hello   Big   World")).toBe("hello-big-world");
  });

  test("handles leading and trailing spaces", () => {
    expect(slugify("  Hello World  ")).toBe("hello-world");
  });

  test("removes punctuation from titles", () => {
    expect(slugify("Hello, World!")).toBe("hello-world");
  });

  test("handles common title characters", () => {
    expect(slugify("What's New?")).toBe("whats-new");
  });

  test("does not leave repeated hyphens", () => {
    expect(slugify("Hello - World")).toBe("hello-world");
  });

  test("handles already slug-like input", () => {
    expect(slugify("hello-world")).toBe("hello-world");
  });

  test("handles empty input", () => {
    expect(slugify("")).toBe("");
  });

  test("does not throw on whitespace-only input", () => {
    expect(slugify("   ")).toBe("");
  });
});
```

# Test-Driven Development

TDD is the red → green loop. This skill is the reference that makes that loop produce tests worth keeping: what a good test is, where tests go, the anti-patterns, and the rules of the loop. Every section applies on every cycle: consult them before and during the loop, not after.

When exploring the codebase, read `CONTEXT.md` (if it exists) so test names and interface vocabulary match the project's domain language, and respect ADRs in the area you're touching.

## What a good test is

Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't. A good test reads like a specification: "user can checkout with valid cart" tells you exactly what capability exists, and it survives refactors because it doesn't care about internal structure.

See [tests.md](tests.md) for examples and [mocking.md](mocking.md) for mocking guidelines.

## Seams: where tests go

A **seam** is the public boundary you test at: the interface where you observe behavior without reaching inside. Tests live at seams, never against internals.

**Test only at pre-agreed seams.** Before writing any test, write down the seams under test and confirm them with the user. No test is written at an unconfirmed seam. You can't test everything, so agreeing the seams up front is how testing effort lands on the critical paths and complex logic instead of every edge case.

Ask: "What's the public interface, and which seams should we test?"

When the shape of that interface is itself in question (how deep the module is, where the seam belongs, what the interface should expose), call the Skill tool with "codebase-design" for the vocabulary. It is the shared source of the module, interface, depth, seam, adapter, leverage and locality terms, and it is a reference to consult, not a session to run.

## Anti-patterns

- **Implementation-coupled**: mocks internal collaborators, tests private methods, or verifies through a side channel (querying the database instead of using the interface). The tell: the test breaks when you refactor but behavior hasn't changed.
- **Tautological**: the assertion recomputes the expected value the way the code does (`expect(add(a, b)).toBe(a + b)`, a snapshot derived by hand the same way, a constant asserted equal to itself), so it passes by construction and can never disagree with the code. Expected values must come from an independent source of truth: a known-good literal, a worked example, the spec.
- **Horizontal slicing**: writing all tests first, then all implementation. Bulk tests verify _imagined_ behavior: you test the _shape_ of things rather than user-facing behavior, the tests go insensitive to real changes, and you commit to test structure before understanding the implementation. Work in **vertical slices** instead: one test → one implementation → repeat, each test a **tracer bullet** that responds to what the last cycle taught you.

## Rules of the loop

- **Red before green.** Write the failing test first, then only enough code to pass it. Don't anticipate future tests or add speculative features.
- **One slice at a time.** One seam, one test, one minimal implementation per cycle.
- **Refactoring is not part of the loop.** It belongs to the review stage (see the `code-review` skill), not the red → green implementation cycle.

If we choose "ignore", implementation becomes:

```js
export function maxValue(rows, column) {
  const values = rows.map(row => row[column]).filter(value => typeof value === "number");

  if (values.length === 0) {
    return null;
  }

  return Math.max(...values);
}
```

You’d now have:

import { maxValue } from "./maxValue";

test("returns the maximum value from a numeric column", () => {
  const rows = [
    { name: "A", score: 10 },
    { name: "B", score: 25 },

test("returns null when there are no rows", () => {

  expect(maxValue(rows, "score")).toBe(20);
