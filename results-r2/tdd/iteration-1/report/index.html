# Test-Driven Development

TDD is the red → green loop. This skill is the reference that makes that loop produce tests worth keeping: what a good test is, where tests go, the anti-patterns, and the rules of the loop. Every section applies on every cycle: consult them before and during the loop, not after.

When exploring the codebase, read `CONTEXT.md` (if it exists) so test names and interface vocabulary match the project's domain language, and respect ADRs in the area you're touching.

## What a good test is

Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't. A good test reads like a specification: "user can checkout with valid cart" tells you exactly what capability exists, and it survives refactors because it doesn't care about internal structure.

See [tests.md](tests.md) for examples and [mocking.md](mocking.md) for mocking guidelines.

## Seams: where tests go

A **seam** is the public boundary you test at: the interface where you observe behavior without reaching inside. Tests live at seams, never against internals.

**Test only at pre-agreed seams.** Before writing any test, write down the seams under test and confirm them with the user. No test is written at an unconfirmed seam. You can't test everything, so agreeing the seams up front is how testing effort lands on the critical paths and complex logic instead of every edge case.

Ask: "What's the public interface, and which seams should we test?"

When the shape of that interface is itself in question (how deep the module is, where the seam belongs, what the interface should expose), call the Skill tool with "codebase-design" for the vocabulary. It is the shared source of the module, interface, depth, seam, adapter, leverage and locality terms, and it is a reference to consult, not a session to run.

## Anti-patterns

- **Implementation-coupled**: mocks internal collaborators, tests private methods, or verifies through a side channel (querying the database instead of using the interface). The tell: the test breaks when you refactor but behavior hasn't changed.
- **Tautological**: the assertion recomputes the expected value the way the code does (`expect(add(a, b)).toBe(a + b)`, a snapshot derived by hand the same way, a constant asserted equal to itself), so it passes by construction and can never disagree with the code. Expected values must come from an independent source of truth: a known-good literal, a worked example, the spec.
- **Horizontal slicing**: writing all tests first, then all implementation. Bulk tests verify _imagined_ behavior: you test the _shape_ of things rather than user-facing behavior, the tests go insensitive to real changes, and you commit to test structure before understanding the implementation. Work in **vertical slices** instead: one test → one implementation → repeat, each test a **tracer bullet** that responds to what the last cycle taught you.

## Rules of the loop

- **Red before green.** Write the failing test first, then only enough code to pass it. Don't anticipate future tests or add speculative features.
- **One slice at a time.** One seam, one test, one minimal implementation per cycle.
- **Refactoring is not part of the loop.** It belongs to the review stage (see the `code-review` skill), not the red → green implementation cycle.
</instructions>

My approach:

### 1. Unit test the signup behavior (most tests)
Treat the mail sender as an external dependency.

Example seam:

```
User signup service

        v
 SMTP provider

Test that:

- a new user signup triggers an email
- the recipient is correct
- the template/type is correct
- the data passed into the template is correct

You can use a fake email sender:

```python
def test_signup_sends_welcome_email():
    email_sender = FakeEmailSender()
    signup_service = SignupService(email_sender=email_sender)

    signup_service.register("alice@example.com")

    assert email_sender.sent_emails == [
        {
            "to": "alice@example.com",
            "template": "welcome"
        }
    ]
```

This test is fast, deterministic, and doesn't depend on network availability.

### 2. Test the email composition separately
If your email generation has logic (HTML rendering, links, localization, personalization), test that at the template boundary:

- subject is correct
- required variables are present
- unsubscribe links/tracking parameters are included if applicable

Avoid asserting the entire generated HTML unless the HTML itself is the product you care about.

### 3. Use a fake SMTP server for integration tests
For a higher-level test, use something like:

- MailHog
- Mailpit
- smtp4dev

Your app talks SMTP, but the server just captures messages locally.

Example flow:

```
Signup API
    |
    v
Application SMTP client
    |
    v
Local fake SMTP server
    |
    v
Assert captured email
```

This catches configuration problems like:

- SMTP authentication issues
- wrong ports
- encoding problems
- MIME formatting issues

without sending real emails.

### 4. Avoid real SMTP in normal CI
A real provider (SendGrid, SES, Gmail SMTP, etc.) introduces:

- flaky network dependencies
- rate limits
- accidental emails to real users
- credential management problems
- slower tests

I’d reserve it for a deployment smoke test, with a dedicated test account.

### 5. A practical test pyramid

| Test | SMTP? | Purpose |
|---|---|---|
| Signup service unit test | No | "Did we request a welcome email?" |
| Email rendering test | No | "Is the message correct?" |
| Integration test with Mailpit/MailHog | Fake SMTP | "Does the email pipeline work?" |
| Production smoke test | Real provider | "Can we actually deliver?" |

The key is to test **your behavior**, not that SMTP itself works. SMTP providers already test SMTP; your code needs tests around the contract you depend on.

output
Following TDD, I’d write regression tests against the **public behavior of `slugify`** before changing the implementation. The current bug is that it only replaces the **first literal space** and doesn’t handle other title inputs well.

I’d start with tests that describe the expected contract:

```js
describe('slugify', () => {
  test('lowercases a title', () => {
    expect(slugify('Hello World')).toBe('hello-world');
  });

  test('replaces multiple spaces with hyphens', () => {
    expect(slugify('Hello Big World')).toBe('hello-big-world');
  });

  test('does not leave repeated hyphens from extra whitespace', () => {
    expect(slugify('Hello   Big   World')).toBe('hello-big-world');
  });

  test('trims leading and trailing whitespace', () => {
    expect(slugify('  Hello World  ')).toBe('hello-world');
  });

  test('handles titles with no spaces', () => {
    expect(slugify('Hello')).toBe('hello');
  });

  test('handles empty titles', () => {
    expect(slugify('')).toBe('');
  });

  test('handles tabs and newlines as whitespace', () => {
    expect(slugify('Hello\tWorld\nToday')).toBe('hello-world-today');
  });
});
```

Depending on the intended slug rules, I’d also add tests for punctuation and non-ASCII titles:

```js
test('removes punctuation if slugs should be URL-safe', () => {
  expect(slugify('Hello, World!')).toBe('hello-world');
});

test('preserves or normalizes unicode according to the slug policy', () => {
  expect(slugify('Café Déjà Vu')).toBe('cafe-deja-vu'); // if transliteration is expected
});
```

The minimum regression test that exposes the existing bug is probably:

```js
test('replaces every space, not just the first one', () => {
  expect(slugify('My Great Title')).toBe('my-great-title');
});
```

That test fails with the current implementation because:

```js
'My Great Title'.toLowerCase().replace(' ', '-')
// => 'my-great title'
```

I’d avoid testing implementation details like “uses regex” or “calls replaceAll”; the tests should lock down the user-visible slug behavior, not the chosen fix.

# Test-Driven Development

TDD is the red → green loop. This skill is the reference that makes that loop produce tests worth keeping: what a good test is, where tests go, the anti-patterns, and the rules of the loop. Every section applies on every cycle: consult them before and during the loop, not after.

When exploring the codebase, read `CONTEXT.md` (if it exists) so test names and interface vocabulary match the project's domain language, and respect ADRs in the area you're touching.

## What a good test is

Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't. A good test reads like a specification: "user can checkout with valid cart" tells you exactly what capability exists, and it survives refactors because it doesn't care about internal structure.

See [tests.md](tests.md) for examples and [mocking.md](mocking.md) for mocking guidelines.

## Seams: where tests go

A **seam** is the public boundary you test at: the interface where you observe behavior without reaching inside. Tests live at seams, never against internals.

**Test only at pre-agreed seams.** Before writing any test, write down the seams under test and confirm them with the user. No test is written at an unconfirmed seam. You can't test everything, so agreeing the seams up front is how testing effort lands on the critical paths and complex logic instead of every edge case.

Ask: "What's the public interface, and which seams should we test?"

When the shape of that interface is itself in question (how deep the module is, where the seam belongs, what the interface should expose), call the Skill tool with "codebase-design" for the vocabulary. It is the shared source of the module, interface, depth, seam, adapter, leverage and locality terms, and it is a reference to consult, not a session to run.

## Anti-patterns

- **Implementation-coupled**: mocks internal collaborators, tests private methods, or verifies through a side channel (querying the database instead of using the interface). The tell: the test breaks when you refactor but behavior hasn't changed.
- **Tautological**: the assertion recomputes the expected value the way the code does (`expect(add(a, b)).toBe(a + b)`, a snapshot derived by hand the same way, a constant asserted equal to itself), so it passes by construction and can never disagree with the code. Expected values must come from an independent source of truth: a known-good literal, a worked example, the spec.
- **Horizontal slicing**: writing all tests first, then all implementation. Bulk tests verify _imagined_ behavior: you test the _shape_ of things rather than user-facing behavior, the tests go insensitive to real changes, and you commit to test structure before understanding the implementation. Work in **vertical slices** instead: one test → one implementation → repeat, each test a **tracer bullet** that responds to what the last cycle taught you.

## Rules of the loop

- **Red before green.** Write the failing test first, then only enough code to pass it. Don't anticipate future tests or add speculative features.
- **One slice at a time.** One seam, one test, one minimal implementation per cycle.
- **Refactoring is not part of the loop.** It belongs to the review stage (see the `code-review` skill), not the red → green implementation cycle.
</instructions>

Implementation:

```js
export function maxValue(rows, column) {
  const values = rows.map(row => row[column]).filter(value => typeof value === "number");

  if (values.length === 0) {
    return null;
  }

  return Math.max(...values);
}
```
