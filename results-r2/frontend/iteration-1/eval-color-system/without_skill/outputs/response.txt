For a developer-tool documentation site, I’d aim for a palette that feels **precise, technical, calm, and trustworthy** rather than “cyberpunk.” Documentation is a reading environment first, so contrast, long-session comfort, and code readability matter more than visual novelty.

## Usage guidance

### Navigation
- Background: `#0F172A`
- Active link: `#22D3EE`
- Inactive links: `#94A3B8`

The cyan accent creates a clear “you are here” indicator without making every element compete for attention.

### Documentation content
- Page background: `#0F172A`
- Body text: `#F8FAFC`
- Headings: `#FFFFFF`
- Supporting text: `#94A3B8`

The contrast hierarchy mirrors how developers scan docs: title → section → explanation → details.

### Code blocks
- Background: `#020617`
- Border: `#1E293B`
- Syntax:
  - Keywords: cyan
  - Strings: green
  - Constants: amber
  - Errors: red

A darker code surface helps examples feel like a familiar IDE environment.

### Buttons
Primary:
- Background: `#22D3EE`
- Text: `#082F49`

Secondary:
- Border: `#334155`
- Text: `#F8FAFC`

The primary action stands out but avoids the common “giant glowing neon button” developer aesthetic.

## Why this works for developer tools

- **Feels technical without cliché:** avoids excessive neon, gradients, and “hacker” imagery.
- **Supports dense information:** muted surfaces let documentation content dominate.
- **Matches developer expectations:** terminal-inspired dark backgrounds, familiar status colors, clear syntax hierarchy.
- **Scales well:** works for API references, SDK docs, dashboards, changelogs, and CLI documentation.
- **Accessible:** the palette naturally supports strong text contrast and semantic status colors.

A good brand personality for this palette would be: **“the reliable engineer sitting next to you, not the flashy startup demo.”**
