## How I would research this question

I would avoid starting from blog opinions or “X is faster” claims. I would frame the question as a **decision problem**: *for what kind of live dashboard workload does WebSocket or Server-Sent Events provide the better engineering tradeoff?*

### 1. Define the dashboard requirements first

Before comparing technologies, I would specify the workload:

**Data flow**
- Is it mostly **server → browser** updates?
  - Example: stock prices, monitoring metrics, analytics charts, operational dashboards.
- Does the browser need to send frequent real-time messages back?
  - Example: collaborative controls, live editing, command consoles.

**Latency requirements**
- Is “near real time” acceptable (100 ms–5 s)?
- Is sub-100 ms interaction required?

**Traffic pattern**
- Number of connected clients:
  - 100?
  - 10,000?
  - 1 million?
- Update frequency:
  - once per minute?
  - 10 events/sec?
  - thousands/sec?

**Operational constraints**
- Existing HTTP infrastructure?
- Load balancers/proxies?
- Need for mobile clients?
- Need for binary data?
- Need for replay/reconnect?

The answer depends heavily on these assumptions.

### A. Official protocol specifications

These are the highest-trust sources.

**WebSocket**
- Read the WebSocket protocol specification:
  - RFC 6455 defines the protocol model, handshake, framing, and full-duplex communication.

- Is communication bidirectional?
- How is connection establishment handled?
- Are binary messages supported?
- What guarantees exist around message framing?

- Is it one-way?
- How does reconnection work?
- How are events formatted?
- What browser APIs exist?
