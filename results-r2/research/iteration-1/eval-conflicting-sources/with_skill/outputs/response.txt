I’d treat the disagreement as a **benchmark validity problem**, not immediately as “one source is wrong.” Two credible benchmarks can both be correct if they measure different things. Benchmarking only helps when the compared metrics, workloads, and conditions are aligned. 

Here’s the process I’d use:

### 1. Define what “fastest” actually means
First I’d ask:

- Fastest for **what workload**?
  - Startup time?
  - Single operation latency?
  - Throughput under load?
  - Memory usage?
  - Large datasets?
  - Small requests?
  - Real production workloads?
- What metric?
  - Mean runtime?
  - p95/p99 latency?
  - Operations per second?
  - CPU time?
  - End-to-end application time?

A library can win one metric and lose another. For example, Library X might have the lowest raw operation latency, while Library Y might process more total requests per second because of better batching.

---

### 2. Inspect the benchmark setup, not just the result

I’d compare:

| Question | Source A | Source B |
|---|---|---|
| Library versions |? |? |
| Runtime/compiler version |? |? |
| Hardware |? |? |
| Operating system |? |? |
| Dataset size |? |? |
| Warmup performed? |? |? |
| Number of runs |? |? |
| Statistical reporting |? |? |

Common benchmark mistakes include small sample sizes, uncontrolled variables, and poor repeatability. 

---

### 3. Check for benchmark bias

I’d look for whether the benchmark accidentally favors one implementation.

Examples:

- Benchmark uses tiny inputs → favors low overhead.
- Benchmark uses huge inputs → favors optimized algorithms.
- Benchmark tests only one feature → ignores other important paths.
- Benchmark is written in a style that maps naturally to one library’s API.

A benchmark is only meaningful if it resembles the intended use case. Specialized benchmarks can produce results that do not generalize. 

---

### 4. Reproduce both benchmarks

I would try to run:

1. Source A’s exact benchmark.
2. Source B’s exact benchmark.
3. A neutral benchmark designed independently.

If:

- X wins A’s benchmark and Y wins B’s benchmark → the benchmarks are measuring different things.
- X wins all three → confidence increases.
- Results flip depending on workload → the answer is “it depends.”

---

### 5. Look at benchmark quality signals

I’d give more weight to benchmarks that:

- publish code,
- publish raw data,
- use realistic workloads,
- test multiple scenarios,
- report variance/error ranges,
- are independently reproducible.

A single “winner” chart is weak evidence.

---

### 6. Determine whether the sources have incentives

I’d check:

- Is Source A maintained by Library X’s authors?
- Is Source B maintained by Library Y’s authors?
- Are there undisclosed configuration choices?
- Were unfavorable tests omitted?

This doesn’t mean either source is dishonest; it just changes how much scrutiny is needed.

---

### 7. Make the conclusion conditional

I would avoid saying:

> “Library X is fastest.”

I’d write something like:

> “Library X is fastest for workload A under conditions B. Library Y is faster for workload C. For our production workload, the relevant benchmark is D, where X/Y wins.”

The goal is not to find the benchmark with the biggest number; it is to identify which benchmark matches the decision you actually need to make.
